## 1. 执行序（六步，按序执行，不得跳步）

### 第①步 读 PRD，提技术特征（不问新问题，先盘存量）

1. 从 PRD 八节摘技术特征，产出《技术特征清单》（会话内呈现，不单独落盘）：

| 特征 | 从 PRD 哪里读 | 摘什么 |
|---|---|---|
| 要存什么数据、多少量 | §三 功能清单＋§六 6.1 数据底线 | 记录类型、条数级别（几十条/几万条）、有没有图片附件 |
| 几个人用 | §二 目标用户 | 第一批人数级（自用/身边十人内/公开多人） |
| 要不要登录、谁能看谁的数据 | §三（权限类功能） | 有无账号体系、隐私底线 |
| 要不要收钱 | §七 约束与依赖（预算/外部依赖） | 收费意图与支付通道依赖 |
| 实时性 | §六 6.1 速度底线 | 「3 秒内出结果」式可感知要求 |
| 设备 | §六 6.1 设备底线＋§七 其他 | 手机/电脑、离线、「数据不能出本机」类红线 |
| 核心流程 | §四 核心流程 | 第⑤步推 API 端点的直接输入 |

2. **红线优先**：PRD §七的用户约束（如「数据不能出本机」）优先级最高——选型与之冲突时按用户约束改，禁硬凑（判据排序见 [../research-funnel.md](../research-funnel.md) §2 第①步）。
3. 评估报告维 1 结论同步入清单：维 1 得分低（核心功能无现成方案）时，第③步选型须把「现成方案/成熟度」权重再调高，并在对照表理由中明写。

### 第②步 骨架快选——走 §2.1 决策树（≤5 问定骨架）

按 §2.1 决策树走：每问先查《技术特征清单》（即 PRD 已确认答案），有就沿用不重问；缺的才当面问用户，一次补问 ≤3 个（C2，禁把树整棵念给用户）。产出：骨架编号（A/B/C/D/D＋收钱）＋前端排版策略，向用户播报一句「按你的需求，应用骨架初步定为＿＿，意思是＿＿」。

### 第③步 三类选型——各走一次调研漏斗（§2.2–§2.4 实例）

按 [../research-funnel.md](../research-funnel.md) 四步法执行，实例裁剪见 §2：

1. **需求化**（第①步）：按骨架把三类调研问题模板填成具体问题，向用户一句话播报要查什么（C5）。
2. **顾问替查**（第②步）：逐类实查 2-4 个候选（草图档减半为 2 个、一轮检索即止），一手来源优先，活跃度用机械事实留痕。
3. **对照呈现**（第③步）：三类各出一张大白话对照表（列规约见 §2.0），每行带来源链接＋检索日期；表后推荐＋一句理由（引用表内事实）；同分以 **AI 友好度**列作 tie-breaker。
4. 检索属 C4 矩阵「直接做」；为验证选型而装依赖属「建议后做」——先说明装什么、为什么，用户不反对才装（本阶段原则上不装，开发是阶段 6 的事）。

### 第④步 技术方案组装

1. 装载模板 [../templates/tech-plan.md](../templates/tech-plan.md)，替换全部 `{{...}}` 占位符，落 `idea2launch/4-tech/技术方案.md`；模板内「填法提示」注释交付时删净。
2. 硬性要求：三件套每件带「为什么选它」（大白话＋引用对照表事实，禁写「业界主流」类无来源话，C1）；工程规范实例化表逐条对照 E1–E5 填「全量采/按栈裁剪」（裁剪留痕，禁静默删，E5-3）；凭据策略只写环境变量名规则，**禁任何真实凭据字面量**（E4-1）；UI 规范迁移节把阶段 3 冻结的 token 体系映射进选定技术栈；里程碑切分 ≥2 个、每个挂用户故事编号（阶段 5 排期的输入）；风险与预案 ≤3 条。
3. 此刻是草稿——写完不等于过闸门（C6 签字产出变更须重签）。

### 第⑤步 API 契约组装

1. 装载模板 [../templates/api-contract.md](../templates/api-contract.md)，落 `idea2launch/4-tech/api-contract.md`。
2. 端点从 PRD §四核心流程推导：主流程每一步「用户做了什么」，映射成「前端动作＋一个后端端点」，或标「本地完成·无端点」；每个端点回链来源用户故事（US-xxx，编号规约见 [../templates/user-stories.md](../templates/user-stories.md)）。
3. 骨架 A（纯静态无后端）时按模板内裁剪注执行：端点表节改写「数据形状契约」（本地存储键名＋数据形状＋导出格式），**留痕不禁默删**。
4. 全文术语首现必译（C2）；「大白话版契约」节每端点一行「它干什么」，给用户看。

### 第⑥步 双闸门：L2 技术栈定稿 ＋ G4-tech 方案签字

顺序写死（[../state-protocol.md](../state-protocol.md) §2.3 G4 行：先双写 `tech-stack` 决策，方案签字 → `signed`）：

**A. L2 决策 `tech-stack`（技术栈定稿）**

1. 向用户大白话念「三件套选择＋为什么」：每件一句「选了＿＿，因为＿＿（引用对照表事实）」；对照表 ≤1 屏已在前步呈现，此处不重贴全表（C2）。
2. **生产档**：按确认页规范（[../confirmation-pages.md](../confirmation-pages.md)）给 2-3 个实质组合选项＋「其他」——默认推荐组合＋次优组合＋「都不满意，补条件重查一轮」（补查轮次上限见 research-funnel §2 第④步）；用户拍板后按七步写入法双写：先 `decisions.log` 追加一行（id=`tech-stack`，`auto:false`，格式见 [../state-protocol.md](../state-protocol.md) §4.1），再写 `state.json` 的 `l2_decisions`（`auto:false`）。
3. **草图档**：自动采用推荐组合并留痕——`auto:true`＋`rationale`（大白话推荐理由）双写落盘，并向用户播报「已自动采用＿＿，理由是＿＿，可随时改」；改＝重新走本 L2（追加新条目，禁删旧条目）。
4. 技术栈定稿后变更＝方向变更（C6）：向用户说明影响面（阶段 5 拆票、阶段 6 开发全部受影响）后重新走本 L2。

**B. L1 闸门 `G4-tech`（方案签字）**

1. 按确认页规范呈现，顺序不可倒：大白话摘要 ≤3 句（做了什么——选型实查＋两份文件；产出在哪——`idea2launch/4-tech/` 两个文件；下一步是什么——阶段 5 排期）＋**后果声明先于选项**（签字＝技术方案定稿进排期，此后改方案＝改已签字产出须重签（C6）；退回＝留在阶段 4 按意见修改）＋**默认四选项：看细节／改了再签／签字／退回**（语义见 [../triggers.md](../triggers.md) L1）。
2. 写回（七步写入法，写路径唯一）：签字 → gates 追加 `G4-tech` `signed`、`current_stage=5`；退回 → 追加 `returned`（附原因）留阶段 4；回退上一闸门 → `G3-design` 追加 `returned` 退回阶段 3。
3. **两档一致**：草图档只自动 L2（上述 A.3），G4 闸门仍须用户真人签，禁代签（C4 矩阵第 5 行）。
4. 连续两次退回 → 触 C3 红旗升级对齐，禁第三次硬交。
5. 签字后按生成项目 AGENTS.md 模板（[../templates/generated-project-AGENTS.md](../templates/generated-project-AGENTS.md) §4）的阶段台账规约追加「阶段 4 摘要卡」。

## 2. 骨架决策树＋三类漏斗实例

### 2.0 对照表列规约（三类共用）

对照表列固定（对齐 [../research-funnel.md](../research-funnel.md) §2 第③步，阶段 4 实例追加「AI 友好度」列、费用列细化为月费用）：

**候选｜它是什么（一句大白话）｜优点（外行人听得懂）｜缺点/约束｜月费用｜AI 友好度｜来源链接＋检索日期**

- 行数：生产档 2-4、草图档 2；每行**必须有来源链接＋检索日期**，没有来源的行不得出现（C1）；术语首现必译（C2：license＝开源使用许可证；自托管＝装在自己电脑/自己服务器上，数据不出门）。
- **AI 友好度（L2 tie-breaker）**：对 AI 智能体开发/自动化的友好度——AI 生态越成熟越加分。机械判据四项，逐项 ✔/✘/未查到：①官方文档完整且有新手教程；②社区教程/问答量大（AI 见得多、写得更顺）；③有一条命令起项目的脚手架或自动化工具；④常见报错可搜到现成解。推荐理由强度相当时，✔ 多者胜出；tie-breaker 结果须在推荐理由中引用具体 ✔ 项。
- **推荐权重**：按角色卡（[../roles/role-4-tech.md](../roles/role-4-tech.md) 职责 1）——推荐项以「新手好上手、好运行、好部署」为第一权重，AI 友好度作同分 tie-breaker，二者不打架：好上手的候选通常 AI 也写得顺。
- **拍板落点**（research-funnel §2 第④步分派表）：decisions.log＋`l2_decisions`（id=`tech-stack`）；草图档自动采用推荐并留痕（`auto:true`＋理由）。

### 2.1 骨架决策树（5 问定骨架）

问序写死；每问先查《技术特征清单》（PRD 已确认答案的映射见括号），有则沿用不重问，缺的当面补问：

| 问# | 问题（大白话） | PRD 答案来源 | 分支 |
|---|---|---|---|
| T1 | 应用要记住东西吗？（关掉再打开，填的内容还在） | 拷问 Q5（内容从哪来） | 不用记 → **骨架 A**；要记 → T2 |
| T2 | 数据只有你自己用，还是很多人隔着网络同时用？ | Q1（给谁用）＋Q6（谁能看）＋§三/§六 6.1（数据量级） | 就自己＋数据小（判据见下注） → **骨架 A**；就自己＋数据不小 → **骨架 B**；多人 → T3 |
| T3 | 要账号登录吗？ | Q7（要不要账号） | 不要 → **骨架 C**；要 → T4 |
| T4 | 要收钱吗？ | Q12（免费还是收钱） | 不收 → **骨架 D**；收 → **骨架 D＋收钱**（标普通红旗 R3：牵支付合规，提醒走正规通道，对齐 stage-1 §2 维 7） |
| T5 | 主要在手机还是电脑用？ | Q10（手机还是电脑） | 不改骨架，只定前端排版策略：响应式一套通吃（默认）／移动优先／桌面优先 |

- T2「数据小」判据（一句话能答，三条全中 → 骨架 A，浏览器自带小仓库 localStorage 足矣）：①要记的东西就几百条以内量级；②不需要跨设备同步（不苛求手机、电脑看到同一份数据）；③丢了能靠手动导出的备份找回来。任何一条不中 → 数据要正经存档，走骨架 B。

| 骨架 | 三件套（前端／后端／数据） | 一句话：适合谁 |
|---|---|---|
| A 纯静态页 | 静态页面／无后端／浏览器自带小仓库（localStorage——存在你自己浏览器里的一小块空间）＋手动导出备份 | 算一算、查一查、不用存档的小工具；或自用＋数据小（判据见 T2 注）的场景 |
| B 单机轻后端 | 页面＋轻后端／单文件数据库（SQLite 类——整个数据库就是电脑里的一个文件，好备份好搬走） | 只有你自己（或同一台电脑前的人）用，但数据要存 |
| C 多人共享·免登录 | 页面＋后端／SQLite 起步（涨了换 PostgreSQL）＋极简共享口令或只读开放 | 一群人共用一个入口，不记「谁是谁」 |
| D 多人＋账号 | 页面＋后端／正经数据库（PostgreSQL 类）＋邮箱登录 | 很多人各用各的账号，数据分人看 |
| D＋收钱 | 骨架 D 全部＋支付通道（帮网站收钱的中间商） | 在 D 之上要收钱——R3 红旗在盘 |

- 骨架只是**起点快选**：定的是漏斗调研问题的范围，最终三件套以第③步实查＋用户拍板为准。
- 树上任何一问与 PRD §七用户红线冲突时，按用户约束改骨架并向用户说明（第①步红线优先）；树面结果与 PRD 已确认的其他工程约束（如手机可用底线、禁过度设计）打架时，同样按约束改骨架并向用户说明一句——树只是快选，红线与工程约束都是硬边界。

### 2.2 漏斗实例·前端框架（页面用什么做）

- **调研问题模板**：「有没有适合新手 Web 应用的页面做法，要求：官方教程多、免费可用、AI 帮写代码写得顺」（按骨架具体化）。
- **候选起点**（实查时可替换，禁直接照抄为本仓推荐，C1）：骨架 A → 「无框架纯手写页面」必入对照（它常是新手最省心的候选）＋至多 2 个轻量增强方案；骨架 B/C/D → 主流组件化框架 2-3 个＋「无框架」作对照项。「要不要框架」本身也是决策，一起上表。
- **对照要点**：上手难度（大白话：学起来像不像学做菜先背菜谱）、改起来难不难、月费用（通常 0）、AI 友好度四项。

### 2.3 漏斗实例·托管方式（应用住在哪）

- **调研问题模板**：「做好的应用放在哪儿别人才能用，要求：新手养得起、好部署（把做好的应用装上去）、月费用低」。
- **候选起点**：本机运行（自己电脑上跑——M1 默认起步形态，交付物即本地运行包）／静态托管（骨架 A 适用，页面文件放专门的免费/低价存放服务）／一体化应用平台（把代码推上去就自动跑起来的「拎包入住」服务）／租服务器自托管（自己租一台 24 小时开机的电脑）。
- **边界**：本阶段只定「往哪儿搬的方向」并留档拍板；真正的部署/上线动作属交付之后用户自主操作（C4 矩阵第 8 行，M1 不代执行云端发布）。
- **对照要点**：月费用（含免费额度够不够用）、数据存在谁家（数据出境/第三方约束如实呈现，联动 PRD §七红线）、出事了能不能把数据搬走。

### 2.4 漏斗实例·数据库（数据存哪里）

- **调研问题模板**：「应用的数据存哪儿，要求：免费起步、以后能导出搬走、AI 帮写查询顺手」。
- **候选起点**：不用独立数据库（localStorage/本地文件——骨架 A 适用）／SQLite（单文件数据库）／PostgreSQL（多人同时用的正经数据库）。同位替代品（如其他主流开源数据库）实查后可入表，禁未查就写入。
- **对照要点**：免费额度、备份与搬走难度（导出＝把数据存成文件带走）、并发上限（大白话：多少人同时写不吵架）、AI 友好度。

### 2.5 约束继承（原型是审核稿，token 必须搬家）

1. **原型阶段的内联 CSS＋token 变量是「审核稿」规矩**：开发阶段的技术栈**不强制沿用**原型的实现方式——原型管「长得对不对」，技术方案管「怎么造出来」。
2. **必须迁移的是 UI 规范 freeze 的 token 体系**（阶段 3 定稿的颜色/字号/间距等设计变量）：映射说明写进技术方案模板「UI 规范迁移」节，阶段 6 开发照此落地——保证做出来的应用和用户签过字的原型长得一致。
3. token 迁移映射表逐变量填：token 名｜原型中的值/形态｜在选定技术栈中的落法（变量名/配置位置）｜备注。缺一项＝迁移没做完。
