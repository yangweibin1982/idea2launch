# 阶段 6 · 开发（Build）· 阶段细则 ○

> 本文是九阶段中第 6 阶段（开发○简版）的执行细则。一句话：智能体换上「开发工程师」角色（角色卡见 [../roles/role-6-build.md](../roles/role-6-build.md)），按批准的票逐张开发——测试先行、过程留痕、按里程碑交验；**首个动作是把 AI 说明书（AGENTS.md）实例化进用户项目**，让后续所有开发会话在同一套规矩下干活。
> 互引分工：职责/输入/输出/禁止事项见角色卡；闸门写回见 [../state-protocol.md](../state-protocol.md)（G6 行：每个里程碑一条 `signed`，同闸门可多条，全部里程碑完成才推进）；装载顺序见 [../triggers.md](../triggers.md)；确认页呈现见 [../confirmation-pages.md](../confirmation-pages.md)。本文只写「这一阶段按什么顺序做、怎么留痕、怎么算做完」。
> 纪律基线：[../disciplines/conduct.md](../disciplines/conduct.md)（C1–C7）＋[../disciplines/engineering.md](../disciplines/engineering.md)（E1–E5 **全量适用**——本阶段是九阶段中唯一整阶段写代码的阶段）。本阶段高频条款：C1 不编造测试结果、C4 装依赖建议后做/跑测试直接做、C6 禁超票面顺手改、E4 凭据零字面量（零妥协）。

## 1. 执行序（四步；第②③④步按里程碑循环）

### 第①步 首个开发动作：实例化 AGENTS.md（先立规矩，再动第一行代码）

1. 按 [../templates/generated-project-AGENTS.md](../templates/generated-project-AGENTS.md) 模板＋[../disciplines/engineering.md](../disciplines/engineering.md) E5 实例化规则，生成用户项目根 `AGENTS.md`：
   - 必选项零裁剪（E5-1：E3 安全基线全文＋E4 凭据纪律全文＋E2 覆盖与留痕＋E1 命名/注释/错误处理）；
   - 按技术栈具体化（E5-2）：格式化工具/测试框架/依赖源——从技术方案 §三 工程实例化表直接抄「怎么落地」列，填成项目实际用的那一个；
   - 裁剪须留痕（E5-3）：确不适用的条目删除后在文尾注记条目＋原因，禁静默删。
2. 台账补写：把已过闸门阶段（1–5）的摘要卡按模板 §4 注释格式补进「阶段台账」（此前各阶段按规约记录的卡）；此后每过闸门追加一卡——让用户日后带入的任何 AI 会话都能接上项目来龙去脉。
3. E4-2 配套落地：`.gitignore` 列入 `.env` 类真实配置文件；建 `.env.example`（键名齐全、值全空或占位符）。
4. 为什么放第一个动作：开发全程（含多代理模式的并行席位）从第一行代码起就与交付物同规（E5 交接班定位）；「实例化在交付确认闸门前完成」（E5-5）由此天然满足，阶段 8 打包时复核（[stage-8-delivery.md](stage-8-delivery.md) 第①步）。

### 第②步 逐票开发（领票→红→绿→记录，循环）

1. **领票**：按排期批次顺序取票；开工播报一句本票做什么＋大约消耗（C5）。
2. **先写失败测试**（TDD 优先，E2-1）：核心业务逻辑先写「怎么算对」的自动检查用例，跑一遍确认失败（红），再写实现让它通过（绿）；界面与纯展示层可豁免先行、不豁免测试。测试框架与目录按技术方案 §三 实例化表；测试运行命令取逐文件形式（禁 `node --test <目录>`——Windows 会把目录误判成单测试文件导致 0 收集，见 §3 判据 6）。
3. **实现自检三对照**：E1 六条基线（语言/格式/命名/注释/目录/错误处理）逐条对照；E3 安全基线（输入校验/输出转义/参数化查询/依赖来源/数据最小化）对照票面涉及面；技术方案 §五 token 迁移映射表——界面票逐变量落地，做出来的页面与签过字的原型长得一致。
4. **装依赖＝建议后做**（C4 矩阵第 6 行＋E3-3）：先说装什么、为什么、来源、大约体积，用户不反对才装。**跑测试/构建＝直接做且留痕**（C4 矩阵第 12 行）。
5. **凭据纪律重申（E4，零妥协）**：代码、配置、示例、测试、文档中禁任何真实凭据字面量——配置值只允许**环境变量读取**或**明显占位符**（形如 `<YOUR_API_KEY>`）；应用确需真实凭据时引导用户本人填入环境变量或密钥服务，智能体不经手不留存（E4-5；C4 矩阵第 9 行）。
6. **票完成**：对照票面完成标准逐条打勾；每条「已通过」对应一次真实运行（C1）；禁超出票面顺手改无关代码——发现该改的先提建议（C4 矩阵第 10 行/C6）。
7. 代码落技术方案 §二 约定目录（`src/` 等），禁散落根目录、禁塞 `idea2launch/`（E1-5——该目录只放流程产出）。

### 第③步 票完成汇报（可攒批）

1. 一次汇报可覆盖多张票，但每票完成标准逐条对照、不虚报（角色卡职责 3）；跑不了的如实标「未验证」，禁写「通过」（C1）。
2. 构建日志落 `idea2launch/6-build/构建日志.md`：时间｜票号｜做了什么｜命令与结果——一条「通过」一行运行证据（E2-4）。
3. 进展说明落 `idea2launch/6-build/进展说明.md`：已完成票／进行中票／未验证项三栏，与盘上实际状态一致（C1）。
4. 失败处理：构建或测试失败 → 记录现象＋已试办法＋建议（C7-4），禁静默重跑冒充通过；`风险登记.md` 有预案的按预案走，没预案的新增一条登记。

### 第④步 里程碑验收闸门 G6-build（里程碑到点触发）

1. **到点判据**：该里程碑全部票完成标准打勾＋应用能跑起来演示（对照技术方案 §六「做完的标志」）。
2. 按确认页规范呈现，顺序不可倒：大白话摘要 ≤3 句（这个里程碑做完了什么——现在能演示什么；证据在哪——`idea2launch/6-build/` 构建日志；下一步是什么——下个里程碑或进质量阶段）＋**后果声明先于选项**（验收＝这批功能定稿，继续下一批；退回＝哪些票返工、返工后重新验收）＋**默认五选项**：看细节／改了再签／签字／退回／回退上一闸门（[../triggers.md](../triggers.md) L1）。
3. 写回（七步写入法，写路径唯一）：验收通过 → gates 追加 `G6-build` `signed` 一条（`note` 记里程碑名——同闸门可多条）；**全部里程碑完成 → `current_stage=7`**；退回 → 追加 `returned`（`note` 记返工票号与原因），按第②③步重走、修完重新验收；回退上一闸门 → `G5-plan` 追加 `returned` 退回阶段 5。
4. **两档一致**：每个里程碑都须用户真人签，草图档不例外，禁代签（C4 矩阵第 5 行）。
5. 每次验收通过追加台账卡（AGENTS.md §4 规约）；连续两次退回同一里程碑 → 触 C3 红旗升级对齐。

## 2. 留痕规约（6-build/ 最低两件＋覆盖底线）

- `idea2launch/6-build/` 最低两件：`构建日志.md`＋`进展说明.md`（格式见第③步）。
- 测试覆盖底线（E2-2）：核心业务逻辑必须有测试覆盖；项目整体行覆盖建议 ≥60%——实测数字写入构建日志，不达标写明原因与欠账位置，禁降到 0、禁编数字（C1）。
- 单次变更控制在单张票内，大批量变更拆批（C2-3）；对外可见的进度说法与 `6-build/` 盘上留痕一致，禁口头超前（C1）。

## 3. 完成判据（机械可判定；在用户项目根执行，全过才进闸门）

| # | 判据 | 机械检查（grep/test，bash） | 通过线 |
|---|---|---|---|
| 1 | 全部批准票有结论 | 对照 `idea2launch/5-plan/tickets/` 清单与 `idea2launch/6-build/进展说明.md` | 每票状态 ∈ {已完成（带证据），进行中，未验证}；禁无结论 |
| 2 | 构建日志带运行证据 | `grep -c "通过" idea2launch/6-build/构建日志.md` ≥ 已完成票数 | 每条「通过」可指认对应运行记录（抽查一条复跑核对，C1） |
| 3 | 覆盖率数字在盘 | `grep -c "覆盖率" idea2launch/6-build/构建日志.md` ≥1 | 实测数字在盘；不达标时有原因与欠账位置 |
| 4 | AGENTS.md 已实例化 | `test -f AGENTS.md && grep -c "凭据纪律" AGENTS.md` | 文件在用户项目根且 E5 必选项节齐全（凭据纪律节 ≥1） |
| 5 | 凭据零字面量 | 按 [../disciplines/engineering.md](../disciplines/engineering.md) E4-3 同款自检命令在项目根执行 | 无命中；命中行逐条复核为占位符或环境变量读取（E4-3 语义），真字面量即不通过 |
| 6 | 测试命令逐文件形式（防 Windows 目录误判） | `grep -nE "node --test [^ .]+( |$)" idea2launch/6-build/构建日志.md`（命中即违例：首个参数无 `.` 文件后缀＝目录形式） | 0 命中——全部 `node --test` 命令为逐文件形式（如 `node --test test/a.test.mjs test/b.test.mjs`，参数带 `.mjs`/`.js` 等文件后缀）；「`node --test ` 后直接跟目录路径」在 Windows 被误判成单测试文件、0 收集（M1 实测坑）。项目未用 node --test 时此条自然通过，其实际测试命令按技术方案 §三 实例化表核对 |
| 7 | 里程碑写回 | gates 中 `G6-build` 条目数＝已验收里程碑数且各带 `note`；全部完成时 `current_stage=7` | 每里程碑一条 `signed` |

- 判据 1–6 在**呈现每个里程碑闸门前**对当批全绿；判据 7 随第④步发生。不全绿＝该里程碑未完成，禁呈现闸门。
- 「完成」的口径＝最后一个里程碑 `signed` 落盘；此前的代码与汇报均为进行时状态（C4 矩阵第 2 行）。
