# 状态机协议：state.json 读写 · 断点续跑 · decisions.log

> 本文是 idea2launch 状态机的唯一权威协议，覆盖五件事：状态怎么读、怎么写、中断后怎么续跑、关键决策怎么留痕、未决缺口怎么登记。
> 字段与类型的机器可读定义见 [state.schema.json](../state.schema.json)（v1）；本文与其字段严格一致，个别扩展字段均走 schema 的附加字段通道（向后兼容约定，见 §6）。
> 铁律一句话：**state.json 是项目的唯一事实源；任何写操作都发生在用户确认之后——写路径唯一。**

## 0. 文件布局

| 文件 | 路径（相对用户项目根） | 作用 |
|---|---|---|
| 状态文件 | `idea2launch/state.json` | 唯一事实源：进行到哪个阶段、闸门签字史、关键决策最新态、未决缺口 |
| 决策日志 | `idea2launch/decisions.log` | 关键决策全历史（append-only，一行一条 JSON） |
| 回滚点 | `idea2launch/state.json.bak` | 每次写入前自动生成的单份快照（滚动覆盖，只留最近一份） |

- 除上述三个文件外，本协议不要求任何其他运行态文件。
- 编码 UTF-8；`state.json` 与 `.bak` 各为一个完整 JSON 对象；`decisions.log` 为 JSON Lines（每行一个独立 JSON 对象）。
- 智能体禁止把进度只记在对话记忆里——「想当然的进度」不算数，盘上有才算。

## 1. 读协议（任何会话开场必做）

**触发时机**：技能被启动或用户回到项目时；以及每个阶段开场固定四步中的第 1 步「读状态」（见 [SKILL.md](../SKILL.md) §2 上下文装载协议——本节即其第 1 步的实施细则）。

**步骤**：

1. 读 `idea2launch/state.json`。**禁止跳过读盘、凭对话记忆续跑。**
2. 按结果分支：
   - **文件缺失** → 没有进行中的项目：走新项目引导（SKILL.md「开工三件事」：能力探测 → 注入询问 → 建档选档）。禁止把对话记忆当成进度。
   - **`schema_version` 大于本插件支持的版本（当前为 1）** → 播报「这个项目是由更新版本的 idea2launch 创建的，请先把插件升级到新版本再继续」，然后停止。**禁止降级覆写**：不得按旧版理解改写该文件、不得删改任何字段。
   - **`schema_version` 缺失或解析失败（文件损坏）** → 进入 §3.3 损坏恢复流程。
   - **正常** → 解析 `current_stage`、`project.tier`、gates 中每道闸门的最新状态、`open_gaps` 中未关闭条目；若 `project.status === "abandoned"`（项目曾被放弃，见 §2.3 G1 行），播报改为：「这个项目《{name}》之前被放下了。想重新启动它吗？重启会从立项评估重新确认一遍。」用户确认重启 → 重新走 G1 签字（追加 `signed` 并把 `project.status` 改回 `"active"`）。
   - 对未知字段一律忽略不报错（schema 向后兼容约定），不得因多出的字段拒绝读档。
3. 向用户大白话播报（模板见 §1.1），必须覆盖三件事：**项目进行到哪；已经完成了什么；现在能做什么**。禁向用户堆内部标识——闸门编号一律翻译成「××已确认」。

### 1.1 续跑播报模板（大白话）

```
欢迎回来！你的项目《{project.name}》现在进行到第 {current_stage} 步：{阶段名}。

已经完成的：
- {已完成闸门的播报用语，逐条列出}

另外有一件之前记下的事还没处理：{open_gaps 未关闭条目的 desc}。现在处理或先放着都行。

接下来我们可以：{当前阶段可做的事，一两句}。要继续吗？
```

阶段名与各闸门的播报用语对照见 §2.3 闸门总表。

## 2. 写协议（写路径唯一）

### 2.1 什么事件允许写

`state.json` 的任何变更只能由下表事件触发。此外一律禁写——尤其禁止：用户闲聊时顺手改、智能体自行「更新进度」、未经确认预写。

| # | 事件 | 前提 | 写什么 |
|---|---|---|---|
| W0 | 建档 | 新项目用户确认项目名＋档位（草图档/生产档）之后 | 写入首版 state.json（8 个顶层字段的初始值；gates / l2_decisions / open_gaps 为空数组） |
| W1 | 闸门事件（L1） | 用户在确认页签字／退回／回退上一闸门 | gates 追加一条；随事件联动的 `current_stage`、`project.tier`、`project.status` 变更；同一笔可联动 `open_gaps` 登记／关闭（写入时机见 §5）与 `project.name` 更新（仅限 G1「调整」重评后随用户确认的新名） |
| W2 | L2 关键决策 | 用户拍板；或草图档按约自动采用推荐项并向用户播报 | l2_decisions 追加一条 ＋ decisions.log 追加一行（§4 双写） |
| W3 | 阶段推进 | 仅随 W1 的 `signed` 事件联动发生（G1 放弃分支除外） | `current_stage` 更新 |
| W4 | 恢复性写 | §3.3 损坏恢复流程，且已向用户播报 | 从 `.bak` 恢复，或经用户确认后的最小重建 |

> 票面所述「仅闸门签字/L2 决策/阶段推进三种事件触发写」即 W1/W2/W3；W0（建档）与 W4（恢复）是流程起点与故障保全所必需的辅助写，同样绑定「确认后写」铁律。
> W1 两项联动写的边界：`open_gaps` 登记／关闭不单独触发写盘，只随闸门事件同笔落盘；`project.name` 更新仅限 G1「调整」（`returned` 重评）后、随用户确认的新名——其他阶段发现项目名不合适，不得顺手改名，须逐道回退至 G1 重做，或登记 `open_gaps` 择机处理。

### 2.2 七步写入法（每次写 state.json 都要走）

1. **确认已发生**：签字／拍板／确认动作已完成（禁预写、禁代签）。
2. **构造新内容**：在内存中基于盘上当前内容生成完整新 JSON（追加式：gates / l2_decisions / open_gaps 只增不改不删，open_gaps 关闭见 §5）。
3. **写临时文件**：完整写入 `idea2launch/state.json.tmp`。
4. **写前自检**：读回 `.tmp`，确认可解析、且本次要改的字段确实在。失败则删除 `.tmp` 中止写入——盘上状态不受影响。
5. **快照**：把当前 `state.json` 复制为 `state.json.bak`（单份滚动回滚点）。
6. **原子替换**：把 `.tmp` 同目录改名覆盖 `state.json`（改名替换，杜绝写到一半的半截文件）。
7. **写后复核**：重读 `state.json` 确认可解析且变更生效；失败则用 `.bak` 覆盖回滚，并向用户播报「写入失败已回退」。

> 双写同笔构造：凡「先 log 后 state」的双写（§2.4 L2 决策、§5 裁决关闭），log 行与 state 字段必须**从同一份数据对象序列化**——先定稿 log 行，state 侧 `chosen`/`rationale`/`at` 逐字取自该行的 `chosen`/`rationale`/`ts`，禁两次独立措辞（同义不同文即双写漂移，§4.3 内容对账是检测网，本条是治本）。

### 2.3 gates 数组规约

**gate 命名**：`G<阶段号>-<阶段短名>`，与九阶段（含各自闸门签字物）一一对应：

| gate 标识 | 阶段 | 闸门签字物 | status 写入时机 | 播报用语 |
|---|---|---|---|---|
| `G1-charter` | 1 立项评估 | 评估报告＋「继续/调整/转草图档/放弃」 | 继续 → `signed`（阶段推进到 2）；调整 → `returned`（留阶段 1 重做）；转草图档 → `signed` 且 `note` 记转档、`project.tier` 改 `draft`；放弃 → `returned` 且 `note` 记「用户放弃项目」、`project.status` 置 `"abandoned"`（附加字段，§6；其后重启＝重新签 G1，见 §1 分支） | 「立项评估已通过」 |
| `G2-requirements` | 2 需求 | PRD 签字页 | 签字 → `signed`（→3）；退回 → `returned` | 「需求文档已确认」 |
| `G3-design` | 3 设计 | 原型＋UI 规范 freeze | 确认冻结 → `signed`（→4）；退回 → `returned`（已拍板的 `ui-direction` 保留；换方向则按 §2.4 追加新决策条目） | 「设计原型和界面规范已定稿」 |
| `G4-tech` | 4 技术 | 技术栈定稿（L2）＋方案签字 | 先按 §4 双写 `tech-stack` 决策，方案签字 → `signed`（→5）；退回 → `returned` | 「技术方案已定稿」 |
| `G5-plan` | 5 计划 | 票批准（L2） | 先双写 `tickets-approval` 决策，闸门 → `signed`（→6）；退回 → `returned` | 「开发计划已批准」 |
| `G6-build` | 6 开发 | 里程碑验收＋票完成汇报（可攒批） | 每个里程碑验收 → `signed` 一条（同 gate 可多条）；全部里程碑完成 → 阶段推进（→7） | 「开发里程碑已验收」 |
| `G7-quality` | 7 质量 | UAT 签字 | 验收通过 → `signed`（→8）；不通过 → `returned`（缺陷回阶段 6 修复） | 「验收测试已通过」 |
| `G8-delivery` | 8 交付 | 交付确认 | 用户确认收到运行包 → `signed`（→9） | 「项目已交付」 |
| `G9-operate` | 9 轻运营 | 无强制闸门 | 本阶段收尾经用户确认后写一条 `skipped`；不写亦合法 | 「进入轻运营」 |

**status 枚举语义**：

| status | 语义 | 约束 |
|---|---|---|
| `signed` | 用户签字通过 | 除 G9 外必随阶段推进；`at` 必填；`note` 建议填 |
| `returned` | 被退回（含回退重做、G1 放弃终局） | `note` 必填原因；`current_stage` 留在（或退回）该阶段 |
| `skipped` | 无强制闸门阶段的确认了结 | 仅限 `G9-operate`；`note` 必填 |

**追加只增**：gates 是按发生顺序追加的历史，禁改写、禁删除既有条目；同一 gate 的最新一条即该闸门当前状态。

**回退上一闸门**（用户在确认页选择回退）：向前一道 gate 追加一条 `returned`（`note` 注明「回退重做」），`current_stage` 退回该阶段；已落档的 L2 决策不删除，重做后若改拍板按 §2.4 追加新条目。

### 2.4 l2_decisions 规约

L2 关键决策共三处（v1 固定）：

| id | 发生阶段 | 决策内容 |
|---|---|---|
| `ui-direction` | 3 设计 | UI 方向拍板 |
| `tech-stack` | 4 技术 | 技术栈定稿 |
| `tickets-approval` | 5 计划 | 开发票批准 |

字段填写：

- `id`：上表三个固定值之一（小写中划线）。同 id 重新拍板 → 追加新条目，读取方以同 id **最后一条**为准，禁删旧条目。
- `chosen`：大白话一句话写清拍板结果（生产档＝用户的选择；草图档＝被采用的推荐项）。
- `auto`：`true` 仅限草图档（自动采用推荐项），且**必须同时给 `rationale`**（大白话推荐理由，同步落 decisions.log），并向用户播报「已自动采用 X，理由：…」；`false`＝用户亲自拍板，生产档必为 `false`；缺省视为 `false`。
- `at`：决策时间，ISO 8601。
- `rationale`：`auto=true` 必填；用户拍板时可记用户附言，无则省略。
- 双写：每次 L2 决策同时追加 decisions.log 一行（§4），顺序＝先 log 后 state。

## 3. 断点续跑协议

### 3.1 续跑判据

- `idea2launch/state.json` 存在、可解析、gates 中至少一条 `signed` → **这是续跑，不是新项目**：按 §1.1 播报后从断点继续，禁重做已签字阶段、禁重新建档、禁重新选档。
- state.json 存在但 gates 为空（刚建档未过 G1）→ 播报「项目刚建档，还没做立项评估」，从阶段 1 开工（属正常续接，不算重开）。
- `project.status === "abandoned"` → 按 §1 放弃分支播报，等用户表态，不自动推进。
- 文件缺失 → §1 读协议的新项目引导分支。

### 3.2 续跑铁律

1. 已 `signed` 的阶段不重做，其产出物直接复用。
2. `returned` 的阶段从该阶段重做；退回原因（`note`）要在开场向用户复述。
3. 中断发生在闸门确认之前 → 本阶段视为未完：产出物在盘上的可续用，确认页重新走一遍。
4. 中断发生在 L2 双写之间（log 已写、state 未写）→ 按 §4.3 对账补齐。

### 3.3 状态损坏三级恢复

1. **一级（state.json 损坏，.bak 可读）**：从 `state.json.bak` 复制恢复，向用户播报「进度档案刚才读不出来，已从备份恢复，进度回到 {bak 中最后的记录时间} 为止」，然后按正常读协议继续。
2. **二级（.bak 也损坏）**：从 decisions.log 全史＋`idea2launch/` 下各阶段产出目录推断最后已知状态，呈报用户：「进度档案损坏了，备份也读不了。根据决策记录和产出文件，你最少做到了……。要我按这个重建进度档案吗？」——**经用户确认后**做最小重建（gates 以 log 与产出物为准，重建条目 `note` 注明「损坏重建」）。
3. **三级（用户选择不重建）**：不动盘上文件，保持已播报的已知状态，等用户指示。

**红线：任何情况下禁止静默重开**——不得因状态读不出就当新项目从头引导。

## 4. decisions.log 规约

### 4.1 行格式（JSONL，每行一个对象，七字段齐全）

```json
{"ts":"2026-10-03T09:30:00+08:00","id":"ui-direction","question":"界面走什么风格方向？","chosen":"卡片流＋大按钮的温暖插画风（推荐项 2）","alternatives":["极简黑白工具风","信息密集表格风"],"auto":true,"rationale":"草图档自动采用：目标用户是社区宠物主人，插画卡片流比密集表格更亲切、非技术用户上手快。"}
```

| 字段 | 说明 |
|---|---|
| `ts` | 决策时间，ISO 8601 |
| `id` | 同 §2.4 的 l2_decisions.id（三个固定值之一），或 `gap-`＋三位序号（缺口裁决行，如 `gap-001`，见 [gap-workbench.md](gap-workbench.md)） |
| `question` | 决策问题原文（大白话） |
| `chosen` | 拍板结果 |
| `alternatives` | 落选候选（字符串数组；无则 `[]`） |
| `auto` | `true`=草图档自动采用；`false`=用户拍板 |
| `rationale` | `auto=true` 必填推荐理由；用户拍板可记附言，无则 `""` |

> 缺口裁决行（`id` 为 `gap-*`）同格式、同七字段：`question`＝缺口 `desc`、`auto` 恒 `false`，各字段取值细则见 [gap-workbench.md](gap-workbench.md) §4。

### 4.2 append-only

- 只追加，禁改写、禁删除历史行。
- 决策变更＝追加新行（`ts` 为新时间），旧行保留即历史。

### 4.3 与 l2_decisions 的关系与对账

- **state.json 存最新态**（同 id 最后一条为准），**decisions.log 存全历史**。
- 双写顺序：先追加 log，再写 state.json。
- 双写同笔构造：log 行与 state 字段从同一份数据对象序列化，禁两次独立措辞（§2.2）。
- 对账两查并做，续跑读档与终态一致性核对均适用：
  1. **时间戳对账（中断补齐）**：若 log 中某 id 的最新行晚于 state.json 中该 id 的最新条目 → 以 log 为准补写 state.json（走 W4 恢复性写，并向用户播报补齐了什么）。
  2. **内容对账（逐字核对）**：时间戳一致时，还须核对 l2_decisions 条目的 `chosen`/`rationale` 与该 id 最新 log 行对应字段**逐字一致**；发现漂移 → **以 log 为准**走 W4 修复（据 log 行重写 state 侧条目），并向用户播报。对账范围限本节三个固定 l2 id；`gap-*` 裁决行不在其列（其 state 侧是 open_gaps 关闭态，核对按 §5）。

## 5. open_gaps 规约（v1 约定）

> schema 对该数组元素结构 v1 不锁定；下表为 v1 协议约定，在此基础上扩展的缺口裁决工作台（缺口分类、裁决流程、裁决写入路径）见 [gap-workbench.md](gap-workbench.md)。

**什么进缺口清单**：

1. 规格未覆盖、用户表示「以后再说」的决策点；
2. 待用户澄清、当前未答的事项；
3. 用户知情后选择带过的小问题（如小缺陷本轮不修）。

**什么不进**：闸门退回原因（走 gates 的 `returned`）、必须当场处理的红旗硬拦项、已闭环的事项。

**v1 字段**：

| 字段 | 说明 |
|---|---|
| `id` | `gap-`＋三位序号（如 `gap-001`），项目内递增、不复用 |
| `desc` | 大白话描述（当时怎么记的，以后就怎么读） |
| `kind` | 分类标记：`feature`（功能缺口）／`decision`（决策待定）／`clarify`（澄清待答）／`accepted`（知情带过），定义见 [gap-workbench.md](gap-workbench.md) §1；缺省视为 `clarify`（向后兼容：旧项目条目无此字段按 `clarify` 读，不补写、不报错） |
| `stage` | 发现时所处阶段号（1-9） |
| `at` | 登记时间，ISO 8601 |
| `status` | `open` ／ `closed` |
| `note` | 关闭时必填：怎么处理的一句话；`open` 时可省略 |

**关闭条件**：用户拍板、澄清落地或明确放弃 → `status` 置 `closed`＋写 `note`。条目保留在数组中不删除（历史可查）。续跑播报只念 `open` 条目。

**写入时机**：登记与关闭均不单独触发写盘——随闸门事件（§2.1 W1）同笔联动落盘（如随 G2 签字把拷问中答「以后再说」的缺口登记落盘，随某闸门签字把已拍板的缺口关闭），「写路径唯一」不因此改变。

**裁决关闭的写入路径**（缺口裁决工作台，见 [gap-workbench.md](gap-workbench.md)）：用户对 `open` 条目拍板裁决（现在就办／登记到下一期／知情带过／撤销）→ 先追加 decisions.log 一行（`id` 用 `gap-`＋三位序号，§4.1），再把该条目置 `closed`＋`note`——同笔落盘，仍走七步写入法（§2.2）。路径按裁决时机二选一：随闸门裁决走 **W1 联动**（闸门事件同一笔落盘，同上）；非闸门时刻裁决走 **W2「用户拍板」决策路径**（先 log 后 state；只动 decisions.log 与 open_gaps，不追加 l2_decisions——l2_decisions 仅限 §2.4 三个固定 L2）。不设新写事件，§2.1 白名单不变。

## 6. 与 schema 及其他协议的衔接

- **字段一致性**：本文所有字段与 `core/state.schema.json`（v1）严格一致。两处经 schema 附加字段通道（`additionalProperties: true`，向后兼容约定）的扩展：`project.status`（§2.3 G1 放弃分支，取值 `active`／`abandoned`，缺省视为 `active`）与 l2_decisions 条目的 `rationale`；未来版本可将其转正为正式字段。
- **装载衔接**：本读协议是主工序「上下文装载协议」（[SKILL.md](../SKILL.md) §2）第 1 步的实施细则；第 2 步起的细则装载按 SKILL.md 指针执行。
- **触发衔接**：技能何时被触发、能力探测怎么做，见 `references/triggers.md`。
- **确认页衔接**：签字／拍板的页面呈现规范（会话提问或 HTML 确认页），见 `references/confirmation-pages.md`。
- **缺口裁决衔接**：open_gaps 的缺口分类（`kind`）、裁决页面（四选项）与裁决写入路径，见 `references/gap-workbench.md`。
