# idea2launch · 触发、探测与装载协议

> 本文件是 [../SKILL.md](../SKILL.md) §2/§4 的全量细则，含三个协议：**三层触发模型**（什么时候必须问用户）、**能力探测协议**（资产盘点七类探测面＋单/多代理怎么定）、**上下文装载协议**（每阶段开场读什么、按什么顺序）。
> 确认环节的具体呈现格式（会话提问/HTML 页）见 [confirmation-pages.md](confirmation-pages.md)；行为约束见 [disciplines/conduct.md](disciplines/conduct.md)。

## 一、显式启动、续跑与存量接入

1. **显式启动**：用户说「用 idea2launch 做一个…」「启动想法落地向导」等显式启动语 → 进入 SKILL.md §0 开工四件事（资产盘点→能力探测→注入询问→建档选档）。
2. **续跑启动**：用户带着已有项目回来（「继续我的项目」）→ 开场读 `idea2launch/state.json` → 播报当前阶段与可做动作 → 从断点继续，不重做已签字阶段（C7）。
3. **存量项目接入**：用户带着一个**已有项目**进来（「帮我把这个项目接进向导来管」），但项目根没有 `idea2launch/state.json`——不是新想法，也不是续跑，走四步：
   - ① **确认意图**：一句话向用户确认「要把这个已有项目接进 idea2launch 流程来管」；用户只是想问问题、没要管流程 → 按 L3 提示，不建档。
   - ② **一屏探测**：扫一眼项目形态——什么语言/框架、多大体量、有没有 `AGENTS.md`（给 AI 看的项目说明书）——结果用一屏大白话播报（C2，术语首现必译）；只读项目结构与配置类文件，禁翻用户私人敏感文件（C4 矩阵第 1 行）。
   - ③ **建档**：确认项目名＋档位后按 [state-protocol.md](state-protocol.md) §2.1 W0 变体建档——`gates` 为空数组**合法**（存量成果不补签历史闸门，禁编造历史，C1）、`current_stage` 按下方「任务落路判定」给（可非 1）。
   - ④ **按任务落阶段**：把用户带来的首个任务按「任务落路判定」落到对应阶段，从那里进入正常流程。
4. **每阶段显式开播**：进入任一阶段前，向用户播报一句——「现在进入阶段 N·角色名，这个阶段会做…，产出会落在…」；让用户对每一步都有预期（G1 决策 11：每个步骤都有显式启动＋提示）。

### 任务落路判定（三条路——存量接入与迭代回访共用）

存量接入建档后、或已交付项目带着新任务回来时，**先判这次的任务落哪条路**，一句话向用户播报判定结果与理由，再动工；判定错了多走的阶段都是消耗（C5）：

| 路 | 任务长什么样 | 去向 |
|---|---|---|
| 小改动 | 改一处文案、修一个小问题、调一个样式——不动需求边界 | 阶段 5 立票（L2 批准）→ 6 开发 → 7 实测，改动经闸门 |
| 新功能/方向变化 | 加功能、换方向、动已签字文档描述的行为 | 阶段 2 增量走（新增用户故事 → 受影响阶段依次重走） |
| 纯咨询 | 只是问怎么用、怎么想，没有要落盘的改动 | 不落阶段，当场答疑；答疑中冒出改动意愿 → 重新判路 |

- **任何迭代改动须用户发起或确认**——检测到「继续做/加功能/顺手改一下」类意图，只提示可做动作与后果，不擅自动工（L3 同款精神，话术见下文 L3 节）。
- 阶段 9 已按「交付后回访」场景写细了前两条路的执行序（[stages/stage-9-operate.md](stages/stage-9-operate.md) §1 第②步）——本节是一般化判定，两处语义一致，执行以阶段细则为出处，不在此重复。

## 二、三层触发模型

| 层 | 内容 | 机制 | 档位差异 |
|---|---|---|---|
| L1 阶段闸门 ×9 | 阶段完成签字 | 确认页硬签字 | 全开（草图档不省） |
| L2 关键决策 ×3 | UI 方向/技术栈/开发票批准 | 确认页或会话提问 | 草图档自动采用推荐项并留痕 |
| L3 意图提示 | 检测开发意图→提示不自动执行 | 每轮对话自查或宿主钩子 | 全开 |

### L1 · 阶段闸门 ×9

| 阶段 | 闸门签字物 | 选项集 |
|---|---|---|
| 1 立项评估 | 评估报告 | 特例集：**继续 / 调整 / 转草图档 / 放弃** |
| 2 需求 | PRD 签字页 | 默认五选项 |
| 3 设计 | 原型＋UI 规范 freeze | 默认五选项 |
| 4 技术 | 技术栈定稿（L2）＋方案签字 | 默认五选项 |
| 5 计划 | 开发票批准（L2） | 默认五选项 |
| 6 开发 | 里程碑验收＋票完成汇报（可攒批，按里程碑多次触发） | 默认五选项 |
| 7 质量 | UAT 签字 | 默认五选项 |
| 8 交付 | 交付确认 | 默认五选项 |
| 9 轻运营 | 无强制闸门 | 不触发；收尾在 `state.json` 留完结状态 |

**签字流程（每闸门固定）**：

1. 呈现大白话摘要（做了什么/产出在哪/下一步是什么）＋后果声明（签字意味着什么/退回意味着什么）——格式见 confirmation-pages.md。
2. 给出选项集，等用户明确选择。默认五选项语义：
   - **看细节**：展示产出原文或关键段落，看完回到本闸门再选。
   - **改了再签**：闸门记 `returned`，按用户意见修改后重新呈现本闸门。
   - **签字**：闸门记 `signed`，`current_stage` 前进；这是唯一的前进路径。
   - **退回**：闸门记 `returned` 并附退回原因，留在本阶段。
   - **回退上一闸门**：向前一道 gate 追加 `returned`（`note` 注明「回退重做」），`current_stage` 退回上一阶段重做——用于「要改上一阶段已签字产出」的场景；阶段 1 特例集不含此项（写回细则见 [state-protocol.md](state-protocol.md) §2.3）。
3. 结果写回 `state.json` 的 `gates`（status/at/note）。写路径唯一：未经闸门/L2 确认不发生任何 `state.json` 变更（C4 第 3 行）。

**纪律红线**：阶段 1 的「放弃」「转草图档」必须出自用户之口（C3）；阶段 7 UAT 只能用户签（C6）；任何档位禁代签（C4 第 5 行）。闸门 ID 落 `state.json` 时的命名规约由状态机实现定稿（schema 草案示例：阶段 1 闸门＝`G0-charter`）。

### L2 · 关键决策 ×3

| 决策 id | 时机 | 问什么 | 草图档行为 |
|---|---|---|---|
| `ui-direction` | 阶段 3 开工时 | 风格方向 2-3 候选选哪个 | 自动采用推荐项并留痕 |
| `tech-stack` | 阶段 4 选型后 | 技术栈定哪套 | 自动采用推荐项并留痕 |
| `tickets-approval` | 阶段 5 拆票后 | 开发票是否批准 | 自动采用推荐拆票并留痕 |

- 生产档：走确认页/会话提问，用户拍板后落 `state.json` 的 `l2_decisions`（`auto: false`），详情追加 `idea2launch/decisions.log`（日期｜决策 id｜选择｜理由）。
- 草图档：自动采用推荐项，落 `l2_decisions`（`auto: true`）＋ decisions.log 留痕，并向用户播报「已自动采用 X，理由是…，可随时改」——**自动的是 L2，不是 L1**：阶段闸门签字在草图档仍然全开（G1 决策 16）。
- L2 决策定稿后再变更＝方向变更：向用户说明影响面并重新走该 L2（签字产出变更须重签，C6）。

### L3 · 意图提示

检测到下列意图时，只提示、不自动执行（零成本防误触发）：

| 意图面（词例） | 提示内容 |
|---|---|
| 继续类（「继续/下一步/接着做」） | 当前阶段与可做动作清单＋各动作后果 |
| 改需求类（「改需求/不对/换成…」） | 影响面（波及哪些已签字阶段）＋给两条路：改上一阶段＝当前闸门选「回退上一闸门」；改更早阶段＝逐道回退（标准话术与写回序列见下） |
| 加功能类（「顺便加一个…」） | 属范围变更→说明对 MVP 边界的影响，请用户确认是否纳入（纳入则回到阶段 2 增量） |
| 开发意图（会话外显，未显式启动本流程） | 提示本插件可用与显式启动语，不自动开工 |

- 提示形态：一两句话＋可选项，禁止倾倒细节；用户不回应则不推进。
- **「改需求类」标准话术与写回序列**：检测到改需求意图 → 先播报影响面（这次改动波及哪些已签字阶段）→ 再给两条路：①改动落在上一阶段——回当前闸门确认页选「**回退上一闸门**」；②要改更早阶段——说明需**逐道回退**，每一道都由用户在确认页确认，不跳步。用户确认后才写回：向前一道 gate 追加 `returned`（`note` 注明「回退重做」）→ `current_stage` 退回 → 按用户意见增量修改 → 重新走该闸门签字。写回语义与 [state-protocol.md](state-protocol.md) §2.3 严格一致，不新增写事件。
- 宿主实现注记：核心定义检测面与提示话术；宿主壳可将其实现为提交前钩子，无钩子机制的宿主由智能体每轮对话自查——两种实现行为一致。

## 三、能力探测协议（资产盘点 · 七类探测面）

**探测什么**：开工资产盘点（[../SKILL.md](../SKILL.md) §0 第 1 件）顺带探测宿主七类能力面——每面一次轻量探测，数秒级，失败即视为「无」，不重试轰炸、不报错。第①面的判定结果落 `agent_mode`（判定与降级细则见本节末 1-5 款）；第②-⑥面的建议与用户拍板（adopt/skip）走**探测-建议-采纳协议**（一页简报、逐项拍板、落 `project.capabilities`），见 [enhancements.md](enhancements.md) §3——一行指针，不在此复制。

| # | 探测面 | 探测动作（大白话） | 结果去向 |
|---|---|---|---|
| ① | 子代理机制 | 查宿主能力清单有无子代理（任务派发）机制；有声明则做一次最小试派验证真可用 | `agent_mode`（multi/single），判定与降级见本节末 1-5 款 |
| ② | 浏览器自动化 | 查宿主有无浏览器控制类工具（能打开网页、截图、点按钮） | 简报行（`project.capabilities`） |
| ③ | 网络检索 | 查宿主有无联网检索/网页读取类工具 | 简报行（`project.capabilities`） |
| ④ | 知识服务 | 发一次轻量健康探测（「算有」的标准见 [enhancements.md](enhancements.md) §3 探测表） | 简报行（`project.capabilities`） |
| ⑤ | 代码索引 | 查工具清单有无代码索引/符号检索类工具，或对项目抽查一个已知符号 | 简报行（`project.capabilities`） |
| ⑥ | 伴生技能 | 查宿主能否装载 markdown 技能（`optional/companion-skills/` 两件是否可用） | 简报行（`project.capabilities`） |
| ⑦ | 插件安装形态 | 查 `<插件目录>/core/` 是否存在——存在即**方式②自包含副本安装**的特征 | 简报附安装形态提示（见下） |

- **安装形态探测（第⑦面）**：检出方式② → 简报中**建议迁移方式①（仓库引用：git pull 即更新、无副本漂移）**；用户拒绝则尊重，不追问（C6）。迁移只改插件自身的更新方式，不影响已建档项目与 `state.json`。
- **零资产出口**：七面探测全部无所得 → 简报明示「**完全可用，以上全是可选增强**」——纯净模式下九阶段流程完整可用（enhancements.md 铁律），禁止为凑简报硬造「发现」。
- 简报的呈现格式（七行能力表＋防呆四禁）用 [templates/asset-inventory-brief.md](templates/asset-inventory-brief.md) 模板。

### 第①面：agent_mode（单/多代理）判定与降级

1. **探测步骤**：① 查宿主能力声明/运行环境清单中有无子代理（任务派发）机制；② 有声明则做一次最小试派（派一个空任务验证真可用）；③ 两步任一失败或无法确认 → 视为 single。
2. **判定**：`multi`＝有子代理机制且试派成功（多代理并行＋辩论增强，属生产档增强）；`single`＝无机制、或试派失败、或探测无法进行——单代理顺序扮演九角色，是本流程的核。
3. **降级纪律**：探测失败**静默降级**——不向用户报错、不打断流程；**留痕**——`agent_mode: "single"` 落 `state.json` 即为留痕，探测失败原因一句话附在开场播报中。
4. **关系澄清**：`multi` 只增强执行方式（并行/辩论），不改变任何闸门、纪律与签字责任；九角色在 single 模式下由同一代理顺序扮演，角色切换时仍须完整过装载协议。
5. **multi 的按阶段职责（三处固定，其余阶段仍单代理）**：multi 不是全程多代理，只在三处把「自己干自己查」拆成「一干一查」：

   | 阶段 | 增强形式 | 跑法（大白话） |
   |---|---|---|
   | 4 技术 | L2 关键决策对抗辩论 | 技术栈定稿前派**正/反方各一**：正方论证推荐项、反方专挑坑，辩果两三句摆进确认页证据（[confirmation-pages.md](confirmation-pages.md) 决策附证），拍板仍在用户 |
   | 6 开发 | 里程碑对抗复核 | 里程碑验收前派**另一代理**复核 diff 与票面（票上说的做了没有、做的里头有没有夹带票外改动），复核结论随票完成汇报一起呈现 |
   | 7 质量 | 独立复测 | 测试报告定稿前派**另一代理**抽跑测试套件，结果与实测报告对账；对不上 → 回炉重测，禁带着对不上的数字出报告（C1） |

   - **档位差异**：生产档**建议启用** multi（三处增强都值回成本）；草图档**单代理**——九角色顺序扮演，三处增强不启用（少一轮派发就少一份消耗，C5）。
   - **边界不变**：辩论/复核/复测只拆「干」与「查」，结论仍经确认页由用户拍板；探测失败即三处增强整体不启用，按第 3 款静默降级 single 并留痕。

## 四、上下文装载协议

每个阶段开场**必读**，顺序写死，不得跳过、不得凭记忆代替读盘：

| 序 | 必读 | 目的 |
|---|---|---|
| 1 | `idea2launch/state.json` | 确认 `current_stage`、`project.tier`、已签字闸门、未决缺口 |
| 2 | `references/roles/role-<N>-<阶段>.md`（本阶段角色卡） | 明确职责/输入/输出/禁止事项 |
| 3 | `references/disciplines/conduct.md`（行为规范包） | 七纪律基线；涉代码/测试/安全时加读 `references/disciplines/engineering.md` |
| 4 | `references/stages/stage-<N>-<阶段>.md`（本阶段细则） | 阶段工序与产出格式 |
| 5 | 阶段专属模块（按角色卡「输入」节指针） | 例：阶段 3 装载 `modules/ui-spec/`（按其 README 顺序） |

- **裁剪规则**：上下文预算不足时，1/3/4 不可裁，2 可只读「职责/禁止事项」两节，5 可延后到用时再读——裁了什么要在开场播报中明示一句。
- **与 SKILL.md §2 的关系**：本表是 SKILL.md 四步装载（读状态→读细则→执行→闸门）中第 2 步的展开，不改变四步顺序。
- 装载完成后才允许执行阶段工序；发现读到的状态与用户口述不一致时，以 `state.json` 为准并当场向用户指出差异（C1/C7）。
