# idea2launch · 触发、探测与装载协议

> 本文件是 [../SKILL.md](../SKILL.md) §2/§4 的全量细则，含三个协议：**三层触发模型**（什么时候必须问用户）、**能力探测协议**（单/多代理怎么定）、**上下文装载协议**（每阶段开场读什么、按什么顺序）。
> 确认环节的具体呈现格式（会话提问/HTML 页）见 [confirmation-pages.md](confirmation-pages.md)；行为约束见 [disciplines/conduct.md](disciplines/conduct.md)。

## 一、显式启动与续跑

1. **显式启动**：用户说「用 idea2launch 做一个…」「启动想法落地向导」等显式启动语 → 进入 SKILL.md §0 开工三件事（能力探测→注入询问→建档选档）。
2. **续跑启动**：用户带着已有项目回来（「继续我的项目」）→ 开场读 `idea2launch/state.json` → 播报当前阶段与可做动作 → 从断点继续，不重做已签字阶段（C7）。
3. **每阶段显式开播**：进入任一阶段前，向用户播报一句——「现在进入阶段 N·角色名，这个阶段会做…，产出会落在…」；让用户对每一步都有预期（G1 决策 11：每个步骤都有显式启动＋提示）。

## 二、三层触发模型

| 层 | 内容 | 机制 | 档位差异 |
|---|---|---|---|
| L1 阶段闸门 ×9 | 阶段完成签字 | 确认页硬签字 | 全开（草图档不省） |
| L2 关键决策 ×3 | UI 方向/技术栈/开发票批准 | 确认页或会话提问 | 草图档自动采用推荐项并留痕 |
| L3 意图提示 | 检测开发意图→提示不自动执行 | 每轮对话自查或宿主钩子 | 全开 |

### L1 · 阶段闸门 ×9

| 阶段 | 闸门签字物 | 选项集 |
|---|---|---|
| 1 立项评估 | 评估报告 | 特例集：**继续 / 调整 / 转草图档 / 放弃** |
| 2 需求 | PRD 签字页 | 默认四选项 |
| 3 设计 | 原型＋UI 规范 freeze | 默认四选项 |
| 4 技术 | 技术栈定稿（L2）＋方案签字 | 默认四选项 |
| 5 计划 | 开发票批准（L2） | 默认四选项 |
| 6 开发 | 里程碑验收＋票完成汇报（可攒批，按里程碑多次触发） | 默认四选项 |
| 7 质量 | UAT 签字 | 默认四选项 |
| 8 交付 | 交付确认 | 默认四选项 |
| 9 轻运营 | 无强制闸门 | 不触发；收尾在 `state.json` 留完结状态 |

**签字流程（每闸门固定）**：

1. 呈现大白话摘要（做了什么/产出在哪/下一步是什么）＋后果声明（签字意味着什么/退回意味着什么）——格式见 confirmation-pages.md。
2. 给出选项集，等用户明确选择。默认四选项语义：
   - **看细节**：展示产出原文或关键段落，看完回到本闸门再选。
   - **改了再签**：闸门记 `returned`，按用户意见修改后重新呈现本闸门。
   - **签字**：闸门记 `signed`，`current_stage` 前进；这是唯一的前进路径。
   - **退回**：闸门记 `returned` 并附退回原因，留在本阶段。
3. 结果写回 `state.json` 的 `gates`（status/at/note）。写路径唯一：未经闸门/L2 确认不发生任何 `state.json` 变更（C4 第 3 行）。

**纪律红线**：阶段 1 的「放弃」「转草图档」必须出自用户之口（C3）；阶段 7 UAT 只能用户签（C6）；任何档位禁代签（C4 第 5 行）。闸门 ID 落 `state.json` 时的命名规约由状态机实现定稿（schema 草案示例：阶段 1 闸门＝`G0-charter`）。

### L2 · 关键决策 ×3

| 决策 id | 时机 | 问什么 | 草图档行为 |
|---|---|---|---|
| `ui-direction` | 阶段 3 开工时 | 风格方向 2-3 候选选哪个 | 自动采用推荐项并留痕 |
| `tech-stack` | 阶段 4 选型后 | 技术栈定哪套 | 自动采用推荐项并留痕 |
| `tickets-approval` | 阶段 5 拆票后 | 开发票是否批准 | 自动采用推荐拆票并留痕 |

- 生产档：走确认页/会话提问，用户拍板后落 `state.json` 的 `l2_decisions`（`auto: false`），详情追加 `idea2launch/decisions.log`（日期｜决策 id｜选择｜理由）。
- 草图档：自动采用推荐项，落 `l2_decisions`（`auto: true`）＋ decisions.log 留痕，并向用户播报「已自动采用 X，理由是…，可随时改」——**自动的是 L2，不是 L1**：阶段闸门签字在草图档仍然全开（G1 决策 16）。
- L2 决策定稿后再变更＝方向变更：向用户说明影响面并重新走该 L2（签字产出变更须重签，C6）。

### L3 · 意图提示

检测到下列意图时，只提示、不自动执行（零成本防误触发）：

| 意图面（词例） | 提示内容 |
|---|---|
| 继续类（「继续/下一步/接着做」） | 当前阶段与可做动作清单＋各动作后果 |
| 改需求类（「改需求/不对/换成…」） | 影响面（波及哪些已签字阶段）＋需要走哪个闸门重签 |
| 加功能类（「顺便加一个…」） | 属范围变更→说明对 MVP 边界的影响，请用户确认是否纳入（纳入则回到阶段 2 增量） |
| 开发意图（会话外显，未显式启动本流程） | 提示本插件可用与显式启动语，不自动开工 |

- 提示形态：一两句话＋可选项，禁止倾倒细节；用户不回应则不推进。
- 宿主实现注记：核心定义检测面与提示话术；宿主壳可将其实现为提交前钩子，无钩子机制的宿主由智能体每轮对话自查——两种实现行为一致。

## 三、能力探测协议

**探测什么**：宿主是否具备子代理机制 → 决定 `agent_mode`（multi/single），落 `state.json`。

1. **探测步骤**：① 查宿主能力声明/运行环境清单中有无子代理（任务派发）机制；② 有声明则做一次最小试派（派一个空任务验证真可用）；③ 两步任一失败或无法确认 → 视为 single。
2. **判定**：`multi`＝有子代理机制且试派成功（多代理并行＋辩论增强，属生产档增强）；`single`＝无机制、或试派失败、或探测无法进行——单代理顺序扮演九角色，是本流程的核。
3. **降级纪律**：探测失败**静默降级**——不向用户报错、不打断流程；**留痕**——`agent_mode: "single"` 落 `state.json` 即为留痕，探测失败原因一句话附在开场播报中。
4. **关系澄清**：`multi` 只增强执行方式（并行/辩论），不改变任何闸门、纪律与签字责任；九角色在 single 模式下由同一代理顺序扮演，角色切换时仍须完整过装载协议。

## 四、上下文装载协议

每个阶段开场**必读**，顺序写死，不得跳过、不得凭记忆代替读盘：

| 序 | 必读 | 目的 |
|---|---|---|
| 1 | `idea2launch/state.json` | 确认 `current_stage`、`project.tier`、已签字闸门、未决缺口 |
| 2 | `references/roles/role-<N>-<阶段>.md`（本阶段角色卡） | 明确职责/输入/输出/禁止事项 |
| 3 | `references/disciplines/conduct.md`（行为规范包） | 七纪律基线；涉代码/测试/安全时加读 `references/disciplines/engineering.md` |
| 4 | `references/stages/stage-<N>-<阶段>.md`（本阶段细则） | 阶段工序与产出格式 |
| 5 | 阶段专属模块（按角色卡「输入」节指针） | 例：阶段 3 装载 `modules/ui-spec/`（按其 README 顺序） |

- **裁剪规则**：上下文预算不足时，1/3/4 不可裁，2 可只读「职责/禁止事项」两节，5 可延后到用时再读——裁了什么要在开场播报中明示一句。
- **与 SKILL.md §2 的关系**：本表是 SKILL.md 四步装载（读状态→读细则→执行→闸门）中第 2 步的展开，不改变四步顺序。
- 装载完成后才允许执行阶段工序；发现读到的状态与用户口述不一致时，以 `state.json` 为准并当场向用户指出差异（C1/C7）。
